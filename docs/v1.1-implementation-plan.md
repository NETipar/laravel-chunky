## F1 — `chunky:doctor` bővítés

**Cél:** a doctor ne csak configot írjon ki, hanem élő ellenőrzéseket
végezzen: queue worker felvesz-e jobot, a broadcast driver elérhető-e, a
zárolás és a tracker működik-e. A supportkérdések nagy része ("miért ragad
`assembling`-ben?") itt derüljön ki. Jelenleg kész: config-kiírás + mindkét
disk write-próbája; a worker- és broadcast-sor csak statikus szöveg.

### Ellenőrzések

1. **Queue worker élő-e.** Új `DoctorProbeJob` (`src/Jobs`): a konstruktorban
   kapott cache-tokent írja be futáskor. A doctor a `chunky.assembly.connection`
   / `queue` szerint dispatch-eli, majd `--wait` másodpercig (default 5)
   pollozza a cache-t.
   - Csak akkor fut, ha `assembly.mode !== 'sync'` (sync módban a jelenlegi
     "no queue worker required" sor marad).
   - `sync` queue-kapcsolatnál azonnal zöld (a dispatch inline fut).
   - Timeout → **ERROR**: "no worker picked up the probe on connection X /
     queue Y within Ns".
2. **Broadcast driver elérhető-e.** Ha `broadcasting.enabled`: próba-broadcast
   a `chunky.doctor` (privát) csatornára try/catch-ben —
   `Broadcast::connection()` + egy minimál esemény. A Pusher/Reverb/Ably
   driverek kapcsolati- és hitelesítési hibái itt kibuknak. `log`/`null`
   driver → info, mindig zöld. Hiba → **ERROR** az üzenettel.
3. **Zárolás.** `LockProvider::withLock('chunky:doctor-probe', fn)` próba —
   a rossz cache-lock setup (pl. cluster-inkompatibilis store) runtime derül
   ki, nem az első éles feltöltésnél.
4. **Tracker.** `database` tracker: a két tábla létezésének ellenőrzése
   (`Schema::hasTable`) — a "elfelejtettem migrálni" eset. `filesystem`
   tracker: a JsonFileStore write+delete próbája a chunk disken.

### Viselkedés

- Minden ERROR-szintű lelet után a parancs `self::FAILURE`-rel tér vissza
  (CI-ban és deploy-pipeline-ban használható kapuként); WARN nem bukik.
- Szignatúra: `chunky:doctor {--wait=5 : Seconds to wait for the queue probe}`.
- A kimeneti formátum marad soronkénti `info`/`warn`/`error`.

### Érintett fájlok + tesztek

`src/Console/DoctorCommand.php`, új `src/Jobs/DoctorProbeJob.php`; feature
tesztek: worker-próba sync connectionnel (zöld), fake queue-val timeout
(ERROR + FAILURE exit), broadcast hiba szimulálása kivételt dobó fake
managerrel, hiányzó tábla → ERROR. README parancs-tábla sor frissítése.

## F2 — Kép-előnézet hook

**Cél:** thumbnail a feltöltés alatt, keretrendszer-függetlenül, függőség
nélkül. Két szint: azonnali objectURL-előnézet + opcionális kicsinyített
thumbnail.

### Core (`@netipar/chunky-core`)

1. **`Uploader.previewUrl(): string | null`** — lazy, első hívásra
   `URL.createObjectURL(this.file)`, utána cache-elt. `null`, ha nem
   `image/*` a fájl vagy nincs `URL` API (SSR-guard). Szándékosan **metódus,
   nem state-mező**: az objectURL létrehozása mellékhatás (revoke-olni kell),
   a state snapshot pedig tiszta adat marad.
2. **Revoke-fegyelem:** a manager az upload evictelésekor / `destroy()`-nál
   hívja a belső `revokePreview()`-t (`URL.revokeObjectURL`). Terminális
   állapot önmagában NEM revoke-ol — a completed-képernyő még mutathatja.
3. **`createThumbnail(file, options)` exportált util** — `{ maxDimension = 256,
   type = 'image/webp', quality = 0.8 }` → `Promise<Blob>`.
   `createImageBitmap` + `OffscreenCanvas` úton, `HTMLCanvasElement`
   fallbackkel; nem-kép fájlra reject. Memóriabarát (a bitmap decode a
   böngésző natív downscale-jét használja `resizeWidth/Height`-tel).

### Wrapperek

- vue3: `useUpload()` visszatérése bővül `previewUrl` computed-del (a state
  változásakor újraértékel); `UploadTray` és `ChunkDropzone` opcionális
  thumbnail-sávot kap (headless slot/prop, alapból ki).
- react: `useUpload()` → `previewUrl` (useMemo az uploader referenciára).
- alpine: `chunkyUpload` komponens `previewUrl` getter.
- Livewire blade: `<img x-show="previewUrl" :src="previewUrl">` minta a
  widget-view-ban (kikommentelt/dokumentált, nem default).

### Tesztek + doksi

Vitest: previewUrl image/* gate, cache + revoke életciklus (createObjectURL
mock happy-dom alatt), createThumbnail happy path + nem-kép reject.
README Frontend szekció + `chunky-frontend` Boost skill egy-egy példasora.

## F3 — Teljes-fájl checksum

**Cél:** end-to-end verifikáció — a kliens a TELJES fájl hash-ét közli, a
szerver az összefűzött eredményt ellenőrzi vele. A chunk-szintű integritás
(ami ma is létezik szerveroldalt) a szállítást védi; ez az összefűzést és a
teljes láncot.

**Tényállás (fontos):** a v1 kliens ma SEMMILYEN checksumot nem küld — a
szerver `checksum` mezője opcionális, és csak akkor ellenőrzött, ha jön.
A teljes-fájl hash kliens-oldali számítása tehát zöldmezős.

### Döntések

- **D1 — hibaút:** sync módban a záró chunk válasza mismatch esetén
  `422 checksum_mismatch` (létező hibakód — a mismatch tipikusan
  kliens-oldali hash-hiba, nem szerverhiba; az 500 `assembly_failed`
  félrevezető volna). Queue módban az upload `failed`-re áll, a status
  endpoint ezt mutatja. Az upload mindkét esetben `failed` terminális
  állapotba kerül, a chunkok a cleanupig megmaradnak (diagnózishoz).
- **D2 — algoritmus:** a teljes-fájl hash **mindig SHA-256**, függetlenül az
  `integrity.algorithm`-tól (az a chunk-szintű mező algoritmusa marad). Így
  nem kell algoritmus-egyeztetést bevezetni a protokollba.

### Protokoll (additív; EN+HU protocol.md + openapi.yaml frissítendő)

- A chunk-kérés (multipart) új opcionális mezője: **`file_checksum`** —
  a teljes fájl SHA-256 hex-e. Bármely chunk-kérésen elfogadott, tipikusan a
  zárón érkezik; a szerver az első nem-üres értéket perzisztálja, a többit
  ignorálja.
- Új configkulcs: **`integrity.require_full_file`** (bool, default `false`) —
  `true` esetén a záró chunk `file_checksum` nélkül `422 validation_failed`.

### Backend

1. `UploadRecord` + tárolás: nullable `file_checksum` mező (DB-migráció
   bővítés + filesystem tracker JSON kulcs + contract suite eset).
2. `UploadChunkRequest`: `file_checksum` → `['nullable', 'string', 'regex:/^[0-9a-f]{64}$/']`.
3. **Hash számítás a MergeStep streamjében:** a chunk-streamek temp-fájlba
   másolása közben `hash_init('sha256')` + `hash_update_stream` — nincs
   második teljes olvasás. A számított hash az `AssemblyState`-be kerül.
4. **IntegrityStep bővítés:** a meglévő méret-ellenőrzés után, ha a rekordon
   van `file_checksum`, összevetés a számítottal; mismatch →
   `ChunkIntegrityException` (a pipeline kompenzál, upload `failed`).
5. Sync válaszút: a `ChunkIntegrityException` renderelése már
   `422 checksum_mismatch` (meglévő envelope-mechanizmus).

### Frontend

1. **Inkrementális SHA-256 beágyazva** (`packages/core/src/internal/sha256.ts`,
   ~100 sor, dependency-free): a WebCrypto `subtle.digest` nem inkrementális,
   GB-os fájl nem bufferelhető. Ismert tesztvektorokkal verifikálva; a
   WebCrypto-val való egyezést a teszt bizonyítja kis fájlokon.
2. **`UploadOptions.fileChecksum?: boolean`** (default `false`, opt-in).
   Bekapcsolva az Uploader a feltöltéssel PÁRHUZAMOSAN, fájl-sorrendben,
   64 MB-os slice-okban hash-eli a fájlt (a fő szálon, await-ekkel szeletelve
   — worker nem kell, a slice-olvasás async). A **záró chunk küldése megvárja
   a hash elkészültét** (lokális olvasás tipikusan gyorsabb a hálózatnál,
   a várakozás ritka).
3. Mismatch a válaszban → `ChunkyError('checksum_mismatch')`, `failed` state —
   a meglévő hibaút, új kliens-logika nem kell.

### Tesztek

Backend: IntegrityStep unit (jó/rossz hash), feature sync-422 + queue-failed,
`require_full_file` mindkét ága, contract suite mindkét trackerrel.
Frontend: sha256 vektorok, hash+upload race (lassú hash → záró chunk várakozik),
opt-out (nem számol, nem küld).

## F4 — Direct-to-S3 multipart upload

**Cél:** a chunkok közvetlenül S3-ba mennek presigned part-URL-ekkel; a
Laravel csak orchestrál (initiate, URL-kiadás, complete, abort). A
legnagyobb skálázási nyereség: a PHP-t se a bájtok, se az összefűzés nem
terheli — az assembly maga az S3 `CompleteMultipartUpload`.

> **Ez a tétel implementáció előtt spec-jóváhagyást igényel** a K2–K5
> kérdésekre. Az alábbi terv a javasolt válaszokkal számol.

### Fő döntések

- **D3 — transport a profil szintjén:** `UploadProfile::transport(): string`
  (`'server'` default | `'direct_s3'`) + config
  `transports.direct_s3.disk` (a cél s3 disk neve). Egy profil vagy direkt,
  vagy szerveres; keverés nincs.
- **D4 — a v1 folyam érintetlen:** szerveres transportnál minden pontosan úgy
  megy, mint ma. A direct út kizárólag additív elemekkel épül: 1 bővített
  válasz + 2 új végpont.
- **D5 — port-absztrakció:** új `DirectUploadTransport` port
  (`create`, `presignParts`, `listParts`, `complete`, `abort`) +
  `S3DirectTransport` adapter az AWS SDK-val (composer `suggest`:
  `aws/aws-sdk-php` vagy `league/flysystem-aws-s3-v3` alól elérve). A
  csomag S3 nélkül is változatlanul működik.

### Protokoll (additív)

1. **Initiate válasz** direct profilnál új `transport` objektummal:

   ```json
   {
     "upload_id": "...", "chunk_size": 8388608, "total_chunks": 120,
     "resumed": false, "uploaded_chunks": [],
     "transport": {
       "mode": "direct_s3",
       "part_urls": { "0": "https://s3...&X-Amz-Signature=...", "...": "..." },
       "expires_at": "2026-07-30T12:00:00Z"
     }
   }
   ```

   A `part_urls` az első adag (max 100) presigned URL; a kliens igény
   szerint kér többet.
2. **Új: `POST {prefix}/upload/{uploadId}/part-urls`** —
   `{ "indexes": [100, 101, ...] }` (max 100/kérés) → friss presigned URL-ek.
   Lejárt URL / retry / resume esetére.
3. **Új: `POST {prefix}/upload/{uploadId}/complete`** —
   `{ "parts": [ { "index": 0, "etag": "\"abc\"" }, ... ] }`. A szerver:
   `CompleteMultipartUpload` → "remote assembly" pipeline: Preflight'
   (állapot-gép: `uploading → assembling`) → Integrity' (HeadObject méret;
   checksum K3 szerint) → ProfileStep (`completed()` hook) → Cleanup'
   (tracker-állapot) → **sync-szerű válasz**: `{ "status": "completed",
   "file": …, "payload": … }` vagy hiba-envelope. Merge/Move nincs — az S3
   végezte.
4. **Cancel** (`DELETE /upload/{id}`) direct esetén `AbortMultipartUpload`-ot
   is hív. A `POST .../chunks` végpont direct uploadra `409 invalid_state`.

### Kényszerek és élek

- **S3 part-szabályok:** min 5 MB/part (utolsó kivétel), max 10 000 part.
  Direct profilnál initiate-kor kikényszerítve: `chunk_size ≥ 5 MB`,
  `total_chunks ≤ 10 000` (különben `422 validation_failed`).
- **Integritás partonként:** a presign `x-amz-checksum-sha256`-ot ír elő — az
  ellenőrzést maga az S3 végzi PUT-kor. A `VerifyChunkIntegrity` middleware a
  direct úton nem játszik.
- **Resume:** fingerprint-találatnál a szerver `ListParts`-szal adja vissza az
  `uploaded_chunks`-ot + friss URL-eket a hiányzókra.
- **Üzemeltetés:** `chunky:cleanup` lejárt direct uploadra `abort`-ot hív;
  a doksi ajánlja az S3 `AbortIncompleteMultipartUpload` lifecycle rule-t
  védőhálónak. `chunky:doctor` direct disk esetén presign-próbát végez.
- **CORS (doksi-kritikus):** a bucket CORS-nak engednie kell a PUT-ot ÉS
  `ExposeHeaders: ETag`-et — enélkül a kliens nem tudja összegyűjteni a
  part-ETageket. Külön szakasz a configuration.md-ben (EN+HU) példa
  CORS-konfigurációval.

### Frontend

Az `Uploader` az initiate válasz `transport.mode`-ja alapján választ
stratégiát — **a hívó kód API-ja változatlan** (upload/pause/resume/cancel/
subscribe ugyanaz). Direct út: part PUT közvetlenül S3-ra (retry/backoff a
meglévő szabályokkal, ETag capture a response headerből), fogyó URL-készlet
utántöltése a `part-urls` végpontról, a végén `complete` hívás; a válasz
feldolgozása azonos a sync záró-válasszal. A `CompletionWatcher` itt nem
kell (a complete szinkron ad eredményt).

### Nyitott kérdések (döntést kér)

- **K2 — státusz-végpont direct alatt:** a `GET /upload/{id}` hívjon-e
  `ListParts`-ot az `uploaded_chunks`-hoz (S3 API-költség kérésenként), vagy
  csak resume-initiate-kor frissüljön? *Javaslat: csak resume-kor; a státusz a
  tracker utolsó ismert állapotát adja, a kliens lokálisan pontos.*
- **K3 — teljes-fájl checksum direct alatt:** az S3 composite
  (checksum-of-checksums) elfogadható-e end-to-end verifikációként? *Javaslat:
  igen, dokumentált eltéréssel — az F3-féle valódi teljes-fájl hash direct
  úton nem kivitelezhető újraolvasás nélkül.*
- **K4 — S3-kompatibilis célok:** MinIO / Cloudflare R2 hivatalosan
  támogatott-e (tesztmátrixba kerül-e)? *Javaslat: MinIO igen (CI-ban
  konténerrel), R2 "best effort" dokumentálva.*
- **K5 — URL-adagolás:** 100 URL/kérés elég-e (10 000 partos maximumnál
  100 kérés)? *Javaslat: igen; a presign olcsó, a válaszméret korlátos marad.*
